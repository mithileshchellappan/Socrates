# Database schema (v19)

SQLite via SQLiteData 1.12 (GRDB 7). Migrations live in `Packages/StudyCore/Sources/StudyCore/Database/Schema.swift`; record types in `Models/Records.swift`. Only the integrator adds migrations. Never edit a migration once it has run on the real library — append a new one.

## Conventions
- Table and column names are `snake_case`; Swift properties are camelCase via `@Column("…")`.
- Primary key: `"id" TEXT PRIMARY KEY NOT NULL ON CONFLICT REPLACE DEFAULT (uuid())`. Create ids in Swift (`UUID()`); stored lowercase.
- Every table has `updated_at`; `RecordStore.save` stamps it. No triggers on library tables (only the search index keeps its FTS tables in step with triggers).
- Dates are TEXT `YYYY-MM-DD HH:MM:SS.SSS` (UTC). Days without a time (`CalendarDay`) are TEXT `YYYY-MM-DD` and are turned into instants only with a time zone. Booleans are INTEGER 0/1. JSON columns are TEXT; BLOB only for opaque data (bookmarks).
- `page_number` is the 1-based deck page ("slide 13"). `*_time`/`time`/`duration` are seconds on a recording's clock (sample 0 = 0.0). `sample_time`/`start_sample`/`frame_count` are frames at `recording.sample_rate`. `*_at` is wall clock. `host_time*` is `mach_absolute_time()`.
- Writes use upsert (`INSERT … ON CONFLICT(id) DO UPDATE`), never `INSERT OR REPLACE` (that deletes the row and fires `ON DELETE CASCADE`).
- Files (PDFs, audio) live in the BlobStore; rows hold `blob_sha256` + `blob_path` (relative to the BlobStore root).

## CloudKit-ready rules (SQLiteData SyncEngine, M7)
- UUID primary key on every library table, no compound keys (`search_chunk` is a device-local index with an INTEGER key and is never synced).
- No `UNIQUE` constraints or unique indexes besides the primary key (tested).
- `ON DELETE` only `CASCADE` or `SET NULL` (tested).
- No foreign-key cycle and no self-reference among synced tables: SQLiteData's `SyncEngine` orders the synced tables by their foreign keys and refuses to start on a cycle (`SchemaError.cycleDetected`; nothing syncs). A reference back (to the row's own table, or to a table that already references this one) is a plain id column without `REFERENCES`, indexed if read by it, and its readers tolerate an id whose row is gone. A synced table never references an unsynced one either (`agent_task.document_id`). Check a library with `python3 .data/pm/sync-schema-check.py <db>` after a migration that adds a foreign key.
- Columns added later must be nullable or `NOT NULL ON CONFLICT REPLACE DEFAULT …`.
- No CloudKit-reserved names (`creationDate`, `modificationDate`, `recordID`, `recordType`, `etag`, …).
- `STRICT` tables.

| search_plan | `SearchPlan` | v9 (M5): the query planner's answer per query (Haiku DE↔EN, "Also searched"). query_key (TEXT primary key, `SearchPlan.key(for:version:)`: "v1:" + the folded query), alternatives (JSON `[String]`), api_call_id, created_at. A query planned once is never sent again |

Triggers `search_chunk_after_insert/delete/update` keep both FTS tables in step. Write chunks with delete + insert, never `INSERT OR REPLACE`. These tables (v9: also `search_vector` and `search_plan`) are listed in `Schema.localTableNames` / `Schema.virtualTableNames`, not `Schema.tableNames` (the library tables CloudKit will sync). ### The recording link (v19)
- **Trust is rows, keys stay home.** Each device's link key is a P-256 key in its own data-protection Keychain (this device only, never synced); its row holds only the public key. A peer is trusted when the SHA-256 of the key it presents in TLS equals the SHA-256, computed by the reader, of an unretired row of the other platform. No fingerprint is stored.
- **One row per key.** A device writes only its own rows. One that had to make a new key inserts a new row and sets `retired_at` on its previous one (whose id it remembers in `Socrates.Link.deviceID`). Rows are never deleted in this milestone (forgetting a device comes later).
- **Only in the iCloud build.** The rows arrive through sync, so a build without it has no link and writes no row. An iCloud account switch stops the link (`CloudSync.accountSwitched`); rows of the old account stay on the device but are no longer read for trust in that run.
- **Files are not rows.** Recordings travel over the link itself into `AppPaths.linkInbox` (`Incoming/<device>/<uuid>.lecture.partial/`), then move into `Recordings/` and are filed as any capture; the phone keeps one receipt per capture beside its outbox (`PhoneCaptures/.link/<uuid>.json`), outside the package.

### Course materials (v18)
- **Files stay in the bank, the course's view syncs.** A file material is a `document` of role `material` (the bank's add path: copied into the BlobStore, ≤ 200 MB, the same SHA-256 one document; the same text, pages, OCR and Undo); a link's README or page text is a role-`material` snapshot document. `course_material` holds the material as the course sees it (one row per course: the same PDF in two courses is one document and two rows), `material_section` its chapters, `material_coverage` which lectures cover them. Rows sync; documents, pages and snapshots never leave the Mac. Role-material documents never show on the Documents screen or in the documents tools (`DocumentRepository.all()` returns role `personal`), and their chunks are kind `material`, never `document`.
- **Search chunks** of a role-material document are windows of one page (`document_id`, `page_number`, kind `material`), never a `course_id`; the course filter joins `course_material.document_id`. Never in the tutor's `material` scope (that one reaches web tools).
- **Sections** keep their row (and so their coverage and summary) across re-reads by `key` (`MaterialRepository.replaceSections`); a key no longer found is deleted with its coverage.
- **Coverage that counts** (`MaterialCoverage.effective`): per (lecture, section) the student's newest row decides (`covers` 0 hides the pair); otherwise every `pass` and `lecturer` row that covers, the strongest one. `pass` / `lecturer` rows belong to their `cover` unit (CASCADE) and are replaced when it re-runs; student rows (`study_unit_id` NULL) are never replaced by a run.
- **Printed pages**: rows and markers carry PDF pages; chips and rows show printed numbers (`CourseMaterial.printedPage(pdfPage:)` with `printed_offset`).
- **Delete** (`MaterialRepository.delete`, one transaction): the materials (sections and coverage cascade), their book further-reading annotations (`SourceRef.materialID`) and book readings; `MaterialDeletion` holds every row and the bank's `DocumentDeletion`s of the documents no other material used, for Undo (`restore`). A course delete cascades `course_material` and with it sections and coverage.
- **Background work**: the card rides on the bank's `document` task (its runner picks the material card for role `material`); chapter summaries are `material_chapter` tasks (`document_id` the material's document, the section in `goal`), queued only by `MaterialRepository.queueChapterSummary`.

### Lecture notes (v16)
- **One writer per version.** A version starts only through `LectureNotesRepository.queue` (Write Again, the agent's write_lecture_notes), `queueIfNeeded` (first open of the notes page or Review's Summary tab: no candidate version yet) or `queueAfterStudyPass` (StudyPass, once the synthesis is written: no current notes, notes from the slides alone, finished notes queued before the lecture's current slides were linked, or a re-run). Each writes the `agent_task` (kind `lecture_notes`, Opus 5.5 medium, no tools) and the `queued` row with the outline from the topic rows in one transaction, never while a version of the lecture is open. The source is `recording` once the synthesis unit is done, else `slides` for a lecture with slides and no recording; otherwise nothing is queued.
- **States.** queued → generating (`begin`; `stream` writes `body` at most every 100 ms) → done (`finish`: checked body and outline, the Check yourself `study_question` rows in the same transaction; the unanswered notes questions of the lecture's other versions are retired) / failed (what came stays) / paused (a usage limit; `paused_until`; resumed from the last complete section) / cancelled (with its task).
- **Current notes**: the newest version that is neither discarded nor cancelled (`LectureNotes.current(of:)`). Previous Version discards the newest (or cancels it while it is written) when an earlier candidate exists; Redo (`restore`) clears `discarded_at`.
- **Format** (`LectureNotesFormat`): Markdown; an overview, then `<!-- section key -->` before each `## heading` (key = 8 hex of the SHA-256 of the topic's folded title, stable across study pass re-runs); typed fences `math`, `diagram`/`mermaid`, `chart`, `slide` (marker, optional `box x y w h`, caption), `quote` (a moment: drawn from the exam hint or highlight row starting at that second), `note` (`[[note 7f3a20c1]]`: written only before nl; since nl (2026-10-21, no migration) the student's notes sit beside the text in the page's Your notes column, the writer places none, the validator drops any, older versions keep theirs and draw them as nothing, and `sections.noteIDs` is written empty), `check` (Q/A/F lines); any other info string is code.
- **Marks** anchor by `section_key` + `exact` (+ `prefix`, `suffix`), matched on folded words (`LectureNotesText`); a mark the current version does not hold is orphaned (a kept answer moves to its section's end with its passage quoted; a highlight hides), never deleted.

### Shared decks (mr)
- **A lecture's slides are a page range of a deck**: its coarse `lecture_deck_span` (no times; `first_page`…`last_page`, both NULL = the whole deck). The newest coarse span (`updated_at`) is the lecture's current slides (`LectureSlides.current`): Review shows only those pages (deck page numbers kept: S21 stays S21), alignment of the lecture's recordings uses only them, and search, citations, the study pass and the coach read the lecture's pages through it. At most one coarse span per lecture and deck (by code: `LectureSlides.link`).
- **One deck, several lectures**: a deck may be linked to any number of lectures of its course, each with its own range ("DC L3 uses DC L2's slides 38–88"). Filing a known deck again links it (never moves it away from the lecture that has it); deleting a lecture, or Undo of a filing, never deletes a deck another lecture still links (`LectureSlides.lectures(usingDeck:)`, Filing's `deckIsUsedElsewhere`).
- **Writes outside filing** (the agent's `link_deck_pages` / `unlink_deck`, continuation detection, their Undo) go through `LectureSlides.link` / `unlink` / `undo` in the caller's transaction, with the change row `DeckLinkResult.change(…)` (`deck_link` / `deck_unlink`, title "DC Lecture 3", summary "Uses DC L2’s slides 38–88" / "No longer uses …", `before` / `after` = lecture, deck, pages, span source; `exists: false` = no link). A link queues `align` jobs for the lecture's transcribed recordings (`LectureSlides.alignmentJobs`, also behind `LectureImporter.alignmentJobs`); an unlink or Undo only when the lecture's current slides changed. Unlinking removes the lecture's timed spans on that deck too. Undo removes the link the change made, or puts the range or the removed link back with the `updated_at` it had (`spanUpdatedAt`: a deck that was not the lecture's current one stays not current), only while the link is still what the change left (`DeckLinkError.changedSince`).
- **Continuation detection**: a transcribed recording whose lecture has no slides is aligned (on device) against the course's recent decks; the best deck and page window above the threshold is linked as `auto` with its confidence and logged as a `deck_link` change (source `transcript`, the best-matching line as quote, model ""). Decks the student turned down for that lecture (`LectureSlides.declinedDeckIDs`: unlinked, or a link undone) are never linked to it again by detection.

### The document bank (v14)
- **Mac only.** The two tables exist on every device (one schema) but never sync (`Schema.macOnlyTableNames`) and only the Mac writes them; the iPhone has no Documents screen. Documents leave the Mac only as delimited context in the student's own agent calls.
- **Adding** copies the file into the BlobStore (never moved or changed); a file whose SHA-256 is already a document's is "known" (nothing added: `DocumentRepository.add` checks and inserts in one write transaction, returning `DocumentAddition(document, isNew)`). The row starts with the file name as its title, kind `other`, text and summary `pending`.
- **Text** is device work on the Mac: `text_state` pending → done (the pages written with the row in one transaction: `DocumentRepository.setText`) or failed (`error`, summary `skipped`); a quit leaves `pending`, read again at launch. Flowing text is cut into "pages" of ≤ 4,000 characters at paragraph ends.
- **Summary**: one `agent_task` of kind `document` (`document_id`) per document, queued only by `DocumentRepository.queueSummary` (one transaction: text done, summary pending, no open task for it), run in code (one Haiku call per document, one at a time: `AgentTaskRepository.claim(…, oneAtATime: [.document])`), writing title, kind, summary, key facts, dates, course_ids and (when the document had none) the outline in one update (`setSummary`). `summary_hash` (`StudyDocument.summaryHash`) keeps the same text from being summarised twice.
- **Delete** (`DocumentBank.delete`): the open `document` task is cancelled first through `AgentTaskRepository.cancel` (the queue stops a running summary), then `DocumentRepository.delete` removes the row in one transaction (pages and search chunks cascade). Undo (`restore`) writes the row and pages back as they were; the bank then reads a pending text and queues a pending summary again. The file stays in the BlobStore until a later launch finds no row using its hash (`BlobUsage.isUsed`).
- **Search**: `document` chunks are windows of one page (`page_number`), `source_id` = `document_id` = the document; never a `course_id` (a course delete must not cascade them, nor a re-cut fail on a course that is gone). The semantic index's unit is the document. Never in the tutor's `material` scope.

### The iPhone and sync (v13)
- **The phone asks, the Mac answers.** A question in the iPhone's agent sheet is an `agent_request` (+ `agent_request_file` rows); the phone never runs Claude. The Mac's pickup (AppAgent) takes pending rows of other devices oldest first, one at a time (`claim` → `send` → `finish` / `fail`), leaves them pending on a usage pause (`release`) and re-queues running ones after a quit (`requeueInterrupted`). The phone shows unanswered requests (`unanswered(conversationID:)`) as the student's bubble with the skeleton line, or "Not answered" with the reason. A new chat on the phone writes its empty `app` conversation row (state finished, title from the first words) and the request names it, so follow-ups asked before the Mac answers stay in it; a request with a NULL conversation is still answered (the Mac starts one and `finish` names it).
- **Sync** (when a build is configured for it): SQLiteData's `SyncEngine` over `Schema.tableNames` except `job` (device-local processing state) and, v14, `Schema.macOnlyTableNames` (the document bank); the device-local tables (`localTableNames`, `virtualTableNames`) never sync. Blobs (decks, audio, images, attachments) do not sync in M7: a synced row whose blob is missing shows as not on this device. A phone configured for sync does not seed the three courses.
- **Phone recordings** are not rows on the phone: they stay `.lecture` packages in `AppPaths.phoneCaptures` until shared to the Mac as a capture bundle (`.lecturebundle`, an Apple Archive of one package), where smart import files them like any capture (course by id, else by the manifest's course name; session by start time).

### The study coach (v12)
- **The plan** is rows (`study_block`) so Today, Study, the agent's `plan_query` and (M7) the iPhone read the same plan. The plan engine rewrites `planned` rows from tomorrow on every replan (`StudyPlanRepository.replacePlanned`, one transaction); today's rows stay once the day began; started, done and skipped rows are never deleted. Today's hero is the day's first open block by `sort_order`; the day's planned total is the sum of its blocks' minutes.
- **Questions** carry their own spaced-repetition card (one per question). Answers are append-only; the card moves only through the scheduler after an answer is graded (`StudyQuestionRepository.updateCard`). A question is never deleted while it has answers: `retired_at` hides it. Mastery dots and Ready come only from `TopicMastery` / `Readiness` (StudyCore `CoachMeasures.swift`), grouped by `TopicKey` (lecture + folded topic title), so questions survive a study pass re-run that replaced the topic rows (`relink`).
- **Quotes** are exact spans of a line's `original_text`; screens draw the line's patches inside the span as ~~old~~ new.
- **Grading**: choices and labels in code (`graded_by = code`, `grading = none`); written answers `pending` until Claude's grade (`setGrade`), failed after 3 attempts; the student's override wins and Claude's score stays in `model_score`.
- **Sessions**: a round asks `question_ids[position]` (a miss is appended later in the same round); a question is answered when an answer row of the session exists for it at that position. An exam's answers are drafts until Submit, then rows; its clock is `active_seconds` plus the time since `resumed_at`.
- **Situational choices** (away days, skips, caps, which exam date, seminar hours, classes not attended) are `plan` memories with a `plan_rule` (PRD "Manage it through the agent"): forgetting the memory drops the rule; the planner forgets expired one-day rules.
- **Credits** are a course fact: `set_course_credits` writes them with an `agent_change` (`course_credits`, before / after) for Undo. The university profile (hours per credit, exam periods, registration windows) is the library's one `university_profile` row (v15, JSON), set through the agent's `set_profile`.

### The one agent (v11)
- **One conversation type** (`app`) on every screen: each user turn's `agent_turn.context` holds what the panel sent besides the words (the `AgentContext`, the context line, the attachments); the message holds the content blocks verbatim (attachments as image/document blocks before the words, an image or a PDF by reference to the bytes sent, then `<catalog>` / `<context>` / `<task_result>` blocks when they changed, then the words). Old `mail_chat`, `tutor` and `deadlines` conversations stay as they are.
- **Automatic changes** go through AppAgent's change log: the target row, its `agent_change` row (and for items and session changes a `tracked_item_source` row) in one transaction. Session changes are tracked items of `isSessionChange` kinds with status `done` once applied, tied by `lecture_session_id`; the session row is changed (`edited_at` set). Undo puts the target back from `before`, stamps `undone_at` (and the source's `undone_at`, dismissing the item); nothing is deleted. M2's open room changes and cancellations keep waiting for Confirm; no new ones are made.
- **Conflicts**: the newest authoritative source wins; the older change gets `superseded_by` and stays, with both sources on the item.
- **Tasks** run ≤ 2 at once in the background (1 under memory pressure); a quit re-queues `running` tasks (`requeueInterrupted`); a usage limit pauses them (`paused_until`). The change marker `[[change 1a2b3c4d]]` (`ChatCitation.change`) names an `agent_change` by its id's first 8 hex.
- **Events** are deduplicated by `source_key` in code (`AgentEventRepository.record`); a failed batch counts an attempt per event (`failed` after 3).
- **Attachments** are BlobStore files (`AgentAttachment.make`: images, PDFs ≤ 32 MB / 100 pages, UTF-8 text ≤ 512 KB; anything else refused).

### Notes and ink (v10)
- **Note bodies** (`note.blocks`, `NoteBlock`): one block per editor paragraph (`paragraph`; `heading` level 1 Title / 2 Heading / 3 Subheading; `bullet` / `numbered` / `checklist` with `level` = indent and `checked`; `quote` with a transcript `source`). Runs are `NoteInline`s: text with marks, `link`, `slide_ref` ("S13"), `time_ref` ("37:59"), `attachment`. Images, sketches and slide clips are inline attachments inside a paragraph (`NoteAttachment` kinds `image`: the original bytes in the BlobStore; `drawing`: an `InkDrawing` JSON blob, content type `socrates.ink` (sketches stored before the rename keep `<prefix>.studyportal.ink`, also read); `slide`: the deck's own PDF blob with the inline's `source` = deck + page). `.image` / `.drawing` / `.slide` blocks are only read (older or imported notes). A note is written only when edited; a block of unstyled text keeps `inlines` nil, so M1 notes re-encode byte for byte.
- **A note's title** is its first block when that is a level-1 heading; untitled notes are named from their anchor ("DC L2 · Slide 15") or first line.
- **Ink coordinates**: `InkDrawing.slide(aspectRatio:)` of the page's crop box with rotation applied (`SlideDeck.aspectRatio(page:)`): 1000 units across, origin top left; widths in the same units.
- **Saving** (as built): a note's editor writes only `blocks` of the row as it is then (`NoteRepository.saveOrDeleteIfBlank`; an emptied note is deleted), 500 ms after typing stops and when it closes, and never an unchanged body; a sketch change stores a new content-addressed blob. `SlideInkEditor` writes a page's drawing 500 ms after the last stroke, erase, undo or redo and at once on page change (an empty drawing deletes the row).
- **Review's Flag** (M6): the student's F writes a `slide_event` of kind `flag` on the recording on screen (`sample_time` = playhead × `sample_rate`, the deck and page on screen); Edit ▸ Undo deletes the row. The aligner ignores flags.

### Search & tutor (v9)
- **Tutor subjects**: a `tutor` conversation is about a lecture (`lecture_id` set, with its `course_id`: Review's Tutor tab), a course (`course_id` set, `lecture_id` NULL: the course's screen) or Search (both NULL). The inspector opens the newest tutor conversation of the screen's subject (`ChatContext.subject`, `ChatSubject(lectureID:courseID:)`); the mail chat (`mail_chat`) is unchanged.
- **Citations** live in the stored answer text as markers (`ChatCitation`: `[[9a7d94d1 S13]]`, `[[9a7d94d1 37:59]]`, `[[web https://…]]`; `9a7d94d1` = the lecture id's first 8 hex). Turns stay verbatim; the chat checks each marker against the rows (and a web URL against the conversation's tool results) before it shows a chip.
- **Agent memory**: written only by the agent's `remember` / `update_memory` / `forget` tools after their quote is verified as the student's own words in that conversation, or by the student in the Memory sheet (`AgentMemoryRepository.edit` / `forget`). Readers skip `forgotten_at`. At most `AgentMemory.activeLimit` (40) active rows.
- **Semantic index**: `search_vector` follows `search_chunk` (reconciled per unit by `text_sha256`, so a re-cut unit embeds only changed text); vectors of another `model` are ignored and replaced in the background.

### The study pass (v8)
What `StudyPassPipeline` (package `StudyPass`) writes, and the student's pins, all in `annotation`:

| What | layer · kind | body | position | extra |
|---|---|---|---|---|
| A slide's summary | ai · `summary` | ≤ 45 words | deck_id + page_number, start_time (its `TimeChip`) | citations: transcript refs |
| The lecture's summary | ai · `summary` | ≤ 90 words | page_number NULL | citations: transcript refs |
| Said in class, not on the slides | ai · `not_on_slides` | ≤ 30 words | start/end_time, page when on a slide | category; citation: transcript ref with the verified quote |
| Exam hint | professor · `exam_hint` | the exact quote | start_time = its first word, page, anchor_text | citation: transcript ref |
| Highlight (stressed, no exam cue) | professor · `highlight` | the exact quote | as exam hint | citation: transcript ref |
| Further reading | ai · `further_reading` | the title | page | citation: web ref (url, title); detail "Barham et al. · SOSP 2003" |
| Topic (coach data, not shown in M4) | ai · `topic` | ≤ 8 words | page_number…last_page, start_time where explained | citation: transcript ref; a topic picked for research also keeps its search query in `detail` and its slide as a `slide` citation (the planner derives the `research:<hash of title, query, slide>` units from these, so an unchanged pick keeps its done unit through a synthesis re-run) |
| The student's pin | user · `comment` | the student's text | page, anchor_x/anchor_y | no study_unit_id |
| A figure slide's description (internal) | ai · `study_figure` | ≤ 25 words | page | written by a read unit for synthesis; never shown |
| A read candidate (internal) | ai · `study_candidate` | `exam`, `highlight` or `said` | the line's page and start_time | `transcript_segment_id` of the line, `category` for `said`; written by a read unit for synthesis; never shown |

- Every pass row carries `study_unit_id`: a unit's results, its patches and its `done` state are written in one transaction; re-running a unit replaces its rows; a unit that no longer exists is deleted and its rows cascade. A done unit whose `input_hash` still matches is never called again.
- `hidden_at` hides an AI or professor item from every surface (Review, pins, scrubber, Today). Readers filter `hidden_at IS NULL`.
- Readers draw only the kinds they know: `study_figure` and `study_candidate` are the read stage's notes for the synthesis (the plan names figure lines and candidates as its inputs), layer ai with `study_unit_id`, and never appear in Review, the pins, the scrubber or Today.
- Patches: `offset` counts characters (grapheme clusters) into `original_text`; `from` must be the exact span there, else the patch is skipped. `reverted_at` keeps a reverted patch (a re-run leaves it reverted while its `from` still matches at its offset). A patch without `api_call_id` is the student's. Save lines through `TranscriptSegment.withPatches` (recomputes `text`, bumps `revision` when it changes); never set `text` by hand.

### Deadlines and the agent (v6)
- Every tracked item write goes through `Deadlines.DeadlineMemory` (package `Agent`): mail, transcript and chat findings are matched across sources, a repeat becomes another source row, and an item goes into the calendar on its own only when its date is verified against the source's exact quote.
- Undo of a source with `previous` puts those fields back; Undo of a source without one dismisses the item (M2 rule).
- `agent_turn` rows are appended by `ConversationRepository.append` only (sequence = last + 1 in the same transaction) and never updated; deleting a conversation cascades to its turns and leaves its chat sources (`conversation_id` SET NULL) and items.
- `transcript_extraction` has one row per recording; a pass re-reads a transcript whose oldest `transcript_segment.updated_at` is after `source_updated_at` (M4: the lines were replaced by a new transcription; study-pass corrections and Revert Correction update single lines, so they do not trigger a deadline re-read).

### Mail (v5)
- No secret is ever stored in the database: `mail_account.keychain_item` is the name of the Keychain item (`SecretKey.uniPassword(username:)`) that holds the password.
- A message copied to two mailboxes is two `mail_message` rows with the same `rfc_message_id`; tracked item sources point at the row and keep the Message-ID, so they survive a re-sync that recreates rows.
- `mailbox` holds the IMAP checkpoint; the sync writes it in the same transaction as the messages it covers. A UIDVALIDITY change sets that mailbox's `uid`s to NULL and re-attaches rows by Message-ID.
- Writes that touch a few columns of a busy row (`setRoute`, `recordExtraction`, `setSeen`, `recordSync`, `editBody`) are column-only updates, so the sync, the router and the reader never revert each other.
- Proposals (room change, cancellation) are `tracked_item` rows with `lecture_session_id` (+ `room`), status open until Confirm (`done`, after the app applied the change to the session) or Discard (`dismissed`). Undo of an auto-added deadline dismisses the item (`in_calendar` false) and stamps its source's `undone_at`; extraction matches dismissed items, so Undo sticks.
- The calendar mirror writes an event for every item with `in_calendar` true, status open and a due date (`wantsCalendarEvent`), `url = socrates://item/<uuid>`, the exact quote as notes, all-day when `is_all_day`; it removes the event once the item no longer wants one (Undo, done, dismissed). Sync state is `calendar_synced_at` as for sessions; the mirror reads only items with `in_calendar` or a `calendar_event_id`.

`lecture_deck_span` is used at two granularities: a coarse span without times ("slides 1–37 of deck X") and, from the aligner, one span per slide visit with `start_time`/`end_time`. `LectureRepository.replaceSpans(lectureID:source:with:)` rewrites one source's spans and keeps the others (stamps, manual).
The coarse span (no times) is the lecture ↔ deck link that alignment reads; one aligner run rewrites every timed span of its recording (`LectureRepository.replaceTimedSpans`). `slide_event` kind `manual` is a "slide starts here" marker set by hand (page nil = off-slide from here); the aligner uses it as given, while `show` stamps are snapped to the nearest pause first.
